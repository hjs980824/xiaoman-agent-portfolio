# 项目案例｜小满：直播电商业务 AI 自动化与 Agent 副驾

## 1. 项目背景

直播中控的工作具有明显的多页面、多任务和强时效特点：开播前检查商品与活动状态；直播过程中需要读取大屏、罗盘和千川等数据，按固定时间记录指标；同时处理商品链接、讲解切换、评论协助和突发异常。

单纯增加人工操作容易造成重复劳动和遗漏；单点 RPA 又容易受页面结构、商品顺序和场次变化影响。项目因此从真实工作流出发，逐步建设数据自动化、SOP 执行、语音触发和 AI 评论副驾。

## 2. 项目目标

- 将重复、规则明确的中控操作沉淀为可复用流程。
- 减少跨页面抄录数据和重复核对。
- 让评论理解能够结合主播口播和商品目录，而不是只看孤立的一条评论。
- 对模型回答和直播工具动作建立边界，必要时保留人工确认。
- 让关键步骤可观察、可复核，失败时能够定位原因。

## 3. 核心模块与完成边界

| 模块 | 已有实现/验证 | 当前边界 |

## 4. AI 副驾的业务链路

副驾不应仅凭评论文本直接回答。设计上需要组合三个上下文来源：

1. 公屏评论：识别用户正在询问颜色、价格、材质、有货情况或多商品比较等意图。
2. 主播口播 / ASR：理解主播刚才正在介绍什么，补充时间上下文。
3. 商品目录与讲解事件：根据本场完整商品列表、商品名称和稳定标识，定位用户真正询问的商品，而不是简单假设当前讲解商品就是目标商品。

随后将识别出的意图与可信商品资料关联，形成候选提示。没有足够依据时应标记未知或请求中控核对，不输出未经验证的商品事实。

离线评测共 32 条样本，30 条返回有效结果，26 条分类匹配，按全部样本计算匹配率为 81.25%。当前结果只用于验证意图分类方向，不作为线上准确率承诺。

## 5. 个人负责内容

- 从直播中控真实工作中发现重复任务与流程断点，提出自动化需求。
- 梳理业务流程、字段定义、指标口径、商品身份和异常场景。
- 设计小满的模块范围、优先级、交互方式和验收标准。
- 规划副驾的多源上下文、意图分类和知识边界。
- 使用 AI Coding 协作推进实现；本人重点负责需求澄清、方案判断、测试用例、运行观察、结果核验和迭代。
- 根据实际验证结果调整范围，例如不让副驾回答当前系统无法可靠读取的单 SKU 实时库存。

## 6. 工程化思考

项目中逐步引入以下工程原则：

- 商品和任务使用稳定标识，不依赖容易变化的显示顺序。
- 对跨场次数据做隔离，避免把不同场次的累计值混在一起。
- 对有副作用的操作先检查目标和状态，再执行并核验结果。
- 区分任务已提交、工具已返回、页面状态已确认三个阶段。
- 记录异常与失败样本，优先修复高频、影响大的问题。
- 先用真实业务流程验证正确性，再评估模型大小、延迟和成本。

## 7. 验收口径

项目验证分为三层，不能混为一谈：

- **离线测试**：验证输入输出、参数校验、规则逻辑和失败分支。
- **模拟页面 / 本地环境**：验证页面交互、工作流顺序和状态变化。
- **真实业务环境**：在获得授权的账号和场次中，核对真实页面状态、实际副作用与异常恢复。

本作品集不声称整套系统已完成所有模块的生产级端到端验收。每项功能的演示应标注其实际验证层级。

## 8. 面试中可以讲的项目价值

小满的核心价值不只是“做了几个自动化脚本”，而是把一线业务问题拆成可实现、可验证的模块：数据有口径，商品有身份，上下文有来源，工具有权限边界，结果有核验方式。AI 负责适合模型处理的理解与辅助决策，确定性操作仍由规则、工具和人工确认共同约束。
